# crossbins

Republishes prebuilt binaries from upstream GitHub releases with normalized filenames.

## Tools tracked

| Tool | Upstream repo | Binary name |
|------|--------------|-------------|
| rg | BurntSushi/ripgrep | `rg` |
| bun | oven-sh/bun | `bun` |
| uv | astral-sh/uv | `uv` |
| yt-dlp | yt-dlp/yt-dlp | `yt-dlp` |
| ffmpeg | BtbN/FFmpeg-Builds; Martin Riedl macOS builds | `ffmpeg` |
| cua-driver | trycua/cua | `cua-driver` |
| cua-driver-uia | trycua/cua | `cua-driver-uia` |
| computer-use-driver | bearlyai/cua | `cua-driver` |
| computer-use-driver-uia | bearlyai/cua | `cua-driver-uia` |

## Naming convention

```
{tool}-{version}-{os}-{arch}[-{variant}][.exe]
```

Examples: `rg-15.1.0-linux-aarch64`, `uv-0.11.3-linux-x86_64-musl`, `yt-dlp-2026.03.17-darwin-universal`

## Download (stable URLs, no auth needed)

Each release includes version-less asset names. GitHub's `/releases/latest` redirect
gives you a stable URL that always points to the most recent published version:

```bash
# Download a binary
curl -fSL https://github.com/bearlyai/crossbins/releases/latest/download/rg-linux-x86_64 -o rg
chmod +x rg

# Check current versions programmatically
curl -fSL https://github.com/bearlyai/crossbins/releases/latest/download/manifest.json | jq .
```

URL pattern: `https://github.com/bearlyai/crossbins/releases/latest/download/{tool}-{os}-{arch}[-{variant}][.exe]`

### Platform naming

| crossbins | Electron / Node.js equivalent |
|-----------|-------------------------------|
| `darwin` | `darwin` |
| `linux` | `linux` |
| `windows` | `win32` |
| `aarch64` | `arm64` |
| `x86_64` | `x64` |
| `i686` | `ia32` |

The `manifest.json` includes a `platform_map` with these translations.

## Usage

### Local testing

```bash
./update.sh          # downloads, normalizes and writes ./output/manifest.json
python3 generate-manifest.py  # rehash local bytes after signing, without publishing
ls -la output/
file output/*        # verify binary types
```

Set `GITHUB_TOKEN` to avoid API rate limits when testing repeatedly.

### Adding a new tool

Two config modes in `binaries.json`:

**Archive-based tools** (rg, bun, uv) — use `asset_prefix` + `triple_map`:
- `name` — short name used in output filenames
- `repo` — GitHub `owner/repo`
- `binary_name` — the executable filename inside the archive
- `asset_prefix` — pattern to match assets (`{VERSION}` is replaced with the resolved version)
- `triple_map` — maps upstream platform strings to `{os, arch, variant}`

**Raw binary tools** (yt-dlp) — use `explicit_assets`:
- `name`, `repo`, `binary_name` — same as above
- `release_tag` — optional exact GitHub release tag; takes precedence over discovery
- `release_tag_pattern` — optional regex to select only matching upstream release tags
- `version_probe_regex` — optional regex with a named `version` capture, resolved from upstream asset names
- `checksum_asset` — optional release asset containing SHA256 checksums to verify before extraction
- `explicit_assets` — list of `{asset_name, source_type, os, arch, variant}` entries. `asset_name`, `asset_regex`, or `url` may use `{VERSION}` from `version_probe_regex`; `checksum_url` may use `{EFFECTIVE_URL}` after redirects are resolved. `source_type` supports `raw`, `zip`, `tar.gz`, and `tar.xz`.
- `checksum_name` and `version_check_regex` — optional direct URL checks for checksum file entries and redirect targets

Any tool may also set:
- `frozen_release` — copy this tool byte for byte from that crossbins release instead of building it (see below)

A release may contain only the tools of the production baseline plus the two new driver entries;
adding a tool also means adding it to `validate-release.py`.

### Updating versions

Run `./update.sh`. Tools with `release_tag` fetch that exact release, including tags older than the most recent 100 releases. Both driver channels must always have exact tags; they never track upstream automatically. Other tools select the latest matching release.

### Frozen tools

A tool with `frozen_release` is carried over unchanged from that crossbins release. The release's
own `manifest.json` is checked in as `baseline/<release>.manifest.json`, with its SHA-256 pinned in
`validate-release.py`, and it is the only source of the tool's expected version, file names,
platforms and hashes. For a frozen tool, `update.sh` never contacts upstream: it downloads both the
versioned and the version-less file from the crossbins release, checks each against the baseline,
and derives the lock entry from the baseline alone. It also checks that the checked-in baseline is
still byte for byte the release's published manifest. Signing and rewrapping skip every frozen file,
and both signing scripts rehash the frozen files afterwards and fail on any change.

The first release with the new driver freezes every tool to `2026-09-21`, the release desktops
read today: rg, bun, uv, yt-dlp, ffmpeg, `cua-driver` and `cua-driver-uia` keep their versions,
file names and signed bytes. Only `computer-use-driver` and `computer-use-driver-uia` are new.

To refresh ordinary tools later, make it its own reviewed release that keeps the accepted driver:

1. Remove `frozen_release` from each tool to refresh in `binaries.json`.
2. Freeze `computer-use-driver` and `computer-use-driver-uia` to the accepted driver release: set
   their `frozen_release` to its tag, check in its `manifest.json` as
   `baseline/<tag>.manifest.json`, and add that file's SHA-256 to `BASELINE_SHA256`.
3. Run `./update.sh` with a new `RELEASE_TAG`.

`cua-driver` and `cua-driver-uia` always stay frozen to `2026-09-21`; the validator refuses
anything else.

## Code signing

### Windows

The published Windows binaries (`*-windows-*.exe`) are Authenticode-signed under Bearly's
identity (`CN = Bearly, Inc.`) using [Azure Trusted Signing](https://learn.microsoft.com/azure/trusted-signing/) —
the **same certificate identity as the Bearly desktop installer**. Signing runs in CI via
[`sign-windows.sh`](sign-windows.sh) using [jsign](https://ebourg.github.io/jsign/), so no
Windows runner is needed, and `publish.sh` refuses to upload any Windows binary that is not
signed as `Bearly, Inc.` (upstream signatures from other publishers do not satisfy the check).

> **Allow-listing in managed environments (BeyondTrust, AppLocker, WDAC, etc.): match the
> publisher identity `Bearly, Inc.` — not a file hash or certificate thumbprint.** Trusted
> Signing issues short-lived leaf certificates (~3-day lifetime, auto-timestamped) that rotate,
> and each binary's hash changes whenever its upstream tool updates. The publisher identity is
> the only value that stays constant across every version, and it matches the installer.

### macOS

The published macOS binaries and app bundles (`*-darwin-*`) are signed with Bearly's
Developer ID Application certificate. App bundles are also notarized and stapled before
publish. `publish.sh` refuses to upload macOS artifacts unless they verify under Bearly's
Apple team identity; app-bundle archives must also carry a stapled notarization ticket.
The PyInstaller-based `yt-dlp` binary is signed with a library-validation exception so its
embedded Python framework can load under the hardened runtime; other raw binaries do not
receive that entitlement.

The new computer-use-driver macOS archive is intentionally rewrapped before signing: upstream `CuaDriver.app`
becomes `Bearly Computer Use Helper.app` with bundle id `com.bearly.computer-use-helper`.
The helper's `AppIcon.icns` is the canonical Bearly Electron icon copied from
`projects/electron/build/icon.icns` in the Bearly repository.
This keeps macOS privacy prompts attributed to Bearly's helper. CUA is MIT licensed; the
required notice is included in the archive root and inside the helper app resources.

Linux binaries are not OS-signed; their release manifest entries carry SHA-256 hashes.

## Automation

Publishing is manual. The Publish binaries workflow remains disabled until deliberately enabled. Once enabled, dispatch it with a unique `release_tag`; `promote` defaults to false. The resulting release has `make_latest=false`, so installed desktop apps keep their current feed. Its manifest URLs point at that immutable release, so staged validation cannot accidentally download production bytes.

After the [Before promoting](#before-promoting) checklist is complete, promote the already staged release without rebuilding:

```bash
gh release edit <release-tag> --repo bearlyai/crossbins --latest
```

A dispatch with `promote=true` promotes only after all artifacts and the manifest upload. Never reuse a release tag: the publisher refuses to overwrite an existing release. A desktop that is already running picks up a promotion, or a rollback, only when it restarts; see [Rollback](#rollback).

Every frozen tool's files are carried over from its crossbins release byte for byte (see
[Frozen tools](#frozen-tools)). `publish.sh` runs `validate-release.py --lock --outputs` before
any release call and `--manifest` on the generated manifest before creating the release. It
fails when any carried-over file differs from the baseline under either of its names, when a
baseline file is missing, when a frozen tool's manifest entry differs from the baseline in any
field other than the release path of its URLs, or when the manifest holds any tool other than the
baseline tools plus the two new driver entries. The baseline manifest's URLs use the
`/releases/latest/download/` path; a staged manifest's URLs use its own
`/releases/download/<release-tag>/` path, so it downloads its own bytes, which are the same bytes.
No workflow input bypasses the guard.

The `computer-use-driver` and `computer-use-driver-uia` entries are Bearly builds from `bearlyai/cua`, pinned to a reviewed `cua-driver-rs-v<version>-bearly.<revision>` tag. Current desktop apps prefer the new regular driver entry, `computer-use-driver`, and fall back to `cua-driver` when it is absent. `computer-use-driver-uia` is published, but no desktop reads it yet. The Windows Program Files helper pair is separate: the desktop app pins it at 0.28.0, and it does not read this feed.

The prepare job runs `python3 test-validate-release.py`, which breaks a stand-in release one way at a time (driver pins, changed bytes under either name, missing files, changed manifest fields, extra or missing tools, an edited baseline file) and checks that each is rejected, then checks real signed files from `2026-09-21`. Each staged release's notes and workflow summary list every tool's baseline and staged version, and whether its bytes are unchanged from the baseline.

To check an actual generated manifest against the production reader functions from desktop 5.2.3 and current master (requires the Bearly checkout and its Electron esbuild dependency):

```sh
node check-desktop-manifest.cjs output/manifest.json /path/to/bearly /path/to/bearly/projects/electron
```

The check exercises the actual source functions for Mac, Windows and Linux, both x64 and arm64. Old desktops select the legacy entries; current master selects the new channel. It checks which entry and version each reader selects and the manifest's shape, not file bytes: `validate-release.py` owns the hashes. The asset's complete URL controls downloads; `download_base` is unused metadata in both readers.

## Rollback

**Fast switch-off: the web flag `computerUseWindowTools`.** Turning it off stops the new window
tools at once, with no app restart. It does not change which driver a desktop runs: the existing
computer-use tools keep running on whatever driver is installed until the app restarts.

**Feed rollback.** Point `latest` back at the production baseline:

```sh
gh release edit 2026-09-21 --repo bearlyai/crossbins --latest
```

Then check that `latest` serves the baseline manifest unchanged:

```sh
gh release view --repo bearlyai/crossbins --json tagName -q .tagName
# 2026-09-21
curl -fsSL https://github.com/bearlyai/crossbins/releases/latest/download/manifest.json | jq -r .release_tag
# 2026-09-21
curl -fsSL https://github.com/bearlyai/crossbins/releases/latest/download/manifest.json | shasum -a 256
# 7f01948cb77b36bfce9a6da3a284f53aeca9eead065b1153ff82df69b9adb3de, the hash of baseline/2026-09-21.manifest.json
```

The manifest hash covers every tool's version, file names and per-platform SHA-256. To also rehash
every version-less file `latest` serves (about 2.6 GB):

```sh
jq -r '.tools[].assets[] | "\(.sha256) \(.url | split("/") | last)"' baseline/2026-09-21.manifest.json |
  while read -r sha name; do
    actual=$(curl -fsSL "https://github.com/bearlyai/crossbins/releases/latest/download/$name" | shasum -a 256 | cut -d' ' -f1)
    [ "$actual" = "$sha" ] || echo "MISMATCH $name"
  done
```

What the feed rollback restores, and when (line numbers are desktop `projects/electron/src/modules/binaries.ts`
and `computerUse.ts` at master `d26987c9`):

- **At once:** fresh installs, and every desktop that loads the feed's manifest from then on, get
  the `2026-09-21` manifest: `cua-driver` 0.28.2 and the same ordinary tools as before.
- **Desktop 5.2.12 that installed the new driver: only after an app restart.** The desktop reads
  the feed at startup (`binaries.ts` 1153), and otherwise only when an installed file fails its
  hash check or a tool has no file for the platform (953, 968). Until then it keeps the manifest it
  has in memory (346) and keeps any installed driver whose version matches it (883, 946). That
  manifest points the driver download at the staged release's own URLs, which keep working. After a
  restart with network, the startup refresh loads the `2026-09-21` manifest, the installed
  0.34.1-bearly.1 no longer matches (634), and the next computer-use start installs `cua-driver`
  0.28.2 (1021–1022). The driver process is started once per app session and reused
  (`computerUse.ts` 348, 376); quitting the app stops it (`computerUse.ts` 810, `main.ts` 123).
  If a driver process from before the restart is still running, stop it. **A user on a broken
  driver must restart the app.**
- **Desktop 5.2.3 to 5.2.11: nothing to recover.** They read only `cua-driver`, `cua-driver-uia`
  and the ordinary tools, which this release carries with the same versions, hashes and file names
  as `2026-09-21`, so moving `latest` either way changes nothing they install. (5.2.3 to 5.2.8
  never re-read a cached manifest at startup; this release does not need them to.)
- **Not affected:** the Windows Program Files helper pair stays at 0.28.0. The desktop pins it, and
  when it is installed the desktop uses it instead of the managed driver (`computerUse.ts` 396).

To run the real reader functions from desktop 5.2.3 to 5.2.11 and current master over a staged
manifest and the baseline:

```sh
node check-desktop-rollback.cjs output/manifest.json /path/to/bearly /path/to/bearly/projects/electron
```

On master it installs the staged driver, moves the feed back, and checks that the running reader
still reports it current; after loading the baseline manifest it reports the driver stale and
selects `cua-driver` 0.28.2, with every other tool still current. For each older reader, going
from the baseline to the staged manifest leaves nothing stale, and every file it selects keeps its
hash and name. It checks reader decisions, not a running app; the live test below does that.

## Before promoting

Desktops always read `latest`: the manifest URL is fixed in `binaries.ts` (266), with no setting,
environment variable or flag to point a desktop at another release. To install a staged driver on a
real 5.2.12 without promoting, seed its manifest cache and let the startup refresh fail once:

1. Quit Bearly. Download the staged release's `manifest.json`
   (`https://github.com/bearlyai/crossbins/releases/download/<release-tag>/manifest.json`) over
   the cached one:
   - Mac: `~/Library/Application Support/Bearly/managed-binaries/manifest.json`
   - Windows: `%APPDATA%\Bearly\managed-binaries\manifest.json`
2. Turn the network off, start Bearly, and wait until its log shows
   `[Binaries] Manifest fetch failed` (within 10 seconds of start). Logs:
   `~/Library/Logs/Bearly/main.log`, `%APPDATA%\Bearly\logs\main.log`.
3. Turn the network back on and start a computer-use task. The log shows
   `[Binaries] CUA Driver 0.34.1-bearly.1 ready at …`, downloaded from the staged release.

On Windows, use a desktop without the Program Files helper; otherwise it runs the 0.28.0 helper
and never installs the managed driver. Because the staged release was never promoted, `latest`
already serves `2026-09-21`: from step 3 on, the app is in the same state as a 5.2.12 whose feed
was just rolled back.

Where to read the driver: the `cua-driver` value in `managed-binaries/bin/.versions.json` under
the folders above; the binary's own `--version`
(Mac: `~/Library/Application Support/Bearly/managed-binaries/bin/Bearly Computer Use Helper.app/Contents/MacOS/cua-driver`,
Windows: `%APPDATA%\Bearly\managed-binaries\bin\cua-driver.exe`); and the running process
(Mac: `pgrep -fl 'cua-driver.*serve'`, Windows PowerShell:
`Get-CimInstance Win32_Process -Filter "Name = 'cua-driver.exe'" | Select-Object ProcessId, ExecutablePath, CommandLine`).
