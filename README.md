# crossbins

Republishes prebuilt binaries from upstream GitHub releases with normalized filenames.

## Tools tracked

| Tool | Upstream repo | Binary name |
|------|--------------|-------------|
| rg | BurntSushi/ripgrep | `rg` |
| bun | oven-sh/bun | `bun` |
| uv | astral-sh/uv | `uv` |
| yt-dlp | yt-dlp/yt-dlp | `yt-dlp` |
| ffmpeg | BtbN/FFmpeg-Builds; Martin Riedl macOS builds | `ffmpeg` |
| cua-driver | trycua/cua | `cua-driver` |
| cua-driver-uia | trycua/cua | `cua-driver-uia` |

## Naming convention

```
{tool}-{version}-{os}-{arch}[-{variant}][.exe]
```

Examples: `rg-15.1.0-linux-aarch64`, `uv-0.11.3-linux-x86_64-musl`, `yt-dlp-2026.03.17-darwin-universal`

## Download (stable URLs, no auth needed)

Each release includes version-less asset names. GitHub's `/releases/latest` redirect
gives you a stable URL that always points to the most recent published version:

```bash
# Download a binary
curl -fSL https://github.com/bearlyai/crossbins/releases/latest/download/rg-linux-x86_64 -o rg
chmod +x rg

# Check current versions programmatically
curl -fSL https://github.com/bearlyai/crossbins/releases/latest/download/manifest.json | jq .
```

URL pattern: `https://github.com/bearlyai/crossbins/releases/latest/download/{tool}-{os}-{arch}[-{variant}][.exe]`

## Usage

### Local testing

```bash
./update.sh          # downloads, normalizes and writes ./output/manifest.json
python3 generate-manifest.py  # rehash local bytes after signing, without publishing
ls -la output/
file output/*        # verify binary types
```

Set `GITHUB_TOKEN` to avoid API rate limits when testing repeatedly.

### Adding a new tool

Two config modes in `binaries.json`:

**Archive-based tools** (rg, bun, uv) — use `asset_prefix` + `triple_map`:
- `name` — short name used in output filenames
- `repo` — GitHub `owner/repo`
- `binary_name` — the executable filename inside the archive
- `asset_prefix` — pattern to match assets (`{VERSION}` is replaced with the resolved version)
- `triple_map` — maps upstream platform strings to `{os, arch, variant}`

**Raw binary tools** (yt-dlp) — use `explicit_assets`:
- `name`, `repo`, `binary_name` — same as above
- `release_tag` — optional exact GitHub release tag; takes precedence over discovery
- `release_tag_pattern` — optional regex to select only matching upstream release tags
- `version_probe_regex` — optional regex with a named `version` capture, resolved from upstream asset names
- `checksum_asset` — optional release asset containing SHA256 checksums to verify before extraction
- `explicit_assets` — list of `{asset_name, source_type, os, arch, variant}` entries. `asset_name`, `asset_regex`, or `url` may use `{VERSION}` from `version_probe_regex`; `checksum_url` may use `{EFFECTIVE_URL}` after redirects are resolved. `source_type` supports `raw`, `zip`, `tar.gz`, and `tar.xz`.
- `checksum_name` and `version_check_regex` — optional direct URL checks for checksum file entries and redirect targets

### Updating versions

Run `./update.sh`. Tools with `release_tag` fetch that exact release, including tags older than the most recent 100 releases. Both driver channels must always have exact tags; they never track upstream automatically. Other tools select the latest matching release.

## Code signing

### Windows

The published Windows binaries (`*-windows-*.exe`) are Authenticode-signed under Bearly's
identity (`CN = Bearly, Inc.`) using [Azure Trusted Signing](https://learn.microsoft.com/azure/trusted-signing/) —
the **same certificate identity as the Bearly desktop installer**. Signing runs in CI via
[`sign-windows.sh`](sign-windows.sh) using [jsign](https://ebourg.github.io/jsign/), so no
Windows runner is needed, and `publish.sh` refuses to upload any Windows binary that is not
signed as `Bearly, Inc.` (upstream signatures from other publishers do not satisfy the check).

> **Allow-listing in managed environments (BeyondTrust, AppLocker, WDAC, etc.): match the
> publisher identity `Bearly, Inc.` — not a file hash or certificate thumbprint.** Trusted
> Signing issues short-lived leaf certificates (~3-day lifetime, auto-timestamped) that rotate,
> and each binary's hash changes whenever its upstream tool updates. The publisher identity is
> the only value that stays constant across every version, and it matches the installer.

### macOS

The published macOS binaries and app bundles (`*-darwin-*`) are signed with Bearly's
Developer ID Application certificate. App bundles are also notarized and stapled before
publish. `publish.sh` refuses to upload macOS artifacts unless they verify under Bearly's
Apple team identity; app-bundle archives must also carry a stapled notarization ticket.
The PyInstaller-based `yt-dlp` binary is signed with a library-validation exception so its
embedded Python framework can load under the hardened runtime; other raw binaries do not
receive that entitlement.

The new computer-use-driver macOS archive is intentionally rewrapped before signing: upstream `CuaDriver.app`
becomes `Bearly Computer Use Helper.app` with bundle id `com.bearly.computer-use-helper`.
The helper's `AppIcon.icns` is the canonical Bearly Electron icon copied from
`projects/electron/build/icon.icns` in the Bearly repository.
This keeps macOS privacy prompts attributed to Bearly's helper. CUA is MIT licensed; the
required notice is included in the archive root and inside the helper app resources.

Linux binaries are not OS-signed; their release manifest entries carry SHA-256 hashes.

## Automation

Publishing is manual. The Publish binaries workflow remains disabled until deliberately enabled. Once enabled, dispatch it with a unique `release_tag`; `promote` defaults to false. The resulting release has `make_latest=false`, so installed desktop apps keep their current feed. Its manifest URLs point at that immutable release, so staged validation cannot accidentally download production bytes.

After verifying the signed artifacts and desktop transport, promote the already staged release without rebuilding:

```bash
gh release edit <release-tag> --repo bearlyai/crossbins --latest
```

A dispatch with `promote=true` promotes only after all artifacts and the manifest upload. Never reuse a release tag: the publisher refuses to overwrite an existing release. Roll back by marking the previous compatible crossbins release latest.

The legacy `cua-driver` and `cua-driver-uia` entries preserve the already signed stock 0.28.2 assets from crossbins release `2026-09-21` byte for byte. Both versioned and version-less asset names are downloaded directly from that immutable release and checked against the pinned per-platform SHA-256 values in `validate-driver-channels.py`. They skip upstream downloads, rewrapping, signing and notarization. Before publishing, the guard rehashes every frozen output and refuses any changed byte; their manifest versions and hashes stay identical to the baseline. No workflow input bypasses the guard.

The `computer-use-driver` and `computer-use-driver-uia` entries are Bearly builds from `bearlyai/cua`, pinned to a reviewed `cua-driver-rs-v<version>-bearly.<revision>` tag. Current desktop apps prefer the new entries and fall back to the legacy entries when the new entries are absent. The separate Windows Program Files helper remains pinned by the desktop app at 0.28.0.

The prepare job runs `python3 validate-driver-channels.py --self-test`, proving that changed legacy tags, discovery patterns, repos, platform sets and hashes are rejected. Each staged release's notes and workflow summary include every tool's baseline and staged version, including ordinary tools that refresh to current upstream releases.

To check an actual generated manifest against the production reader functions from desktop 5.2.3 and current master (requires the Bearly checkout and its Electron esbuild dependency):

```sh
node check-desktop-manifest.cjs output/manifest.json /path/to/bearly /path/to/bearly/projects/electron
```

The check exercises the actual source functions for Mac, Windows and Linux, both x64 and arm64. Old desktops resolve the unchanged legacy bytes; current master resolves the new channel. The asset's complete URL controls downloads; `download_base` is unused metadata in both readers.
